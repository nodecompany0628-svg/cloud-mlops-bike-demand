# 결과 평가

평가 코드는 [bikeml/evaluate.py](../bikeml/evaluate.py), 서비스 검사 코드는 [bikeml/servicecheck.py](../bikeml/servicecheck.py)이고, 결과는 [results/evaluation/](../results/evaluation/)와 [results/service_check/](../results/service_check/)에 있다.

## 1. 평가 자료와 판단 기준

평가하기 전에 정했다.

- 평가 자료: 2012-09-01 ~ 2012-12-31의 2,888시간. 학습에 쓰지 않은 미래 기간이다.
- 비교 대상 (같은 평가 자료)
  - `baseline_mean`: 학습 자료 전체의 시간당 평균(179.3)을 항상 답한다.
  - `baseline_hour_mean`: 학습 자료의 (시각, 근무일 여부)별 평균을 답한다. 출퇴근 시간 효과를 반영하는 단순 방법이다.
- 지표: 운영 담당자는 몇 대가 대여될지로 계획하므로 단위가 그대로 남는 지표를 골랐다.
  - MAE = 평균(|예측 - 실제|), 대/시간. 기본 지표
  - RMSE = √평균((예측 - 실제)²), 대/시간. 큰 오차에 더 민감하다
  - bias = 평균(예측 - 실제). 음수면 적게 예측한 것이다
  - 일별 합계 MAE = 하루 합계끼리 비교한 MAE, 대/일
- 합격 기준 ([config/pipeline.json](../config/pipeline.json)의 `evaluation.criteria`)
  1. 두 기준 방법보다 MAE가 낮을 것
  2. 시간대 평균 기준보다 MAE를 30% 이상 줄일 것

기준을 넘지 못하면 `evaluate` 단계가 실패로 끝난다. `deploy`는 현재 모델로 합격한 기록이 없으면 진행하지 않는다.

## 2. 품질 결과

`python -m bikeml run local`의 결과([results/evaluation/metrics.json](../results/evaluation/metrics.json))다. 평가 자료의 실제 평균은 240.2 대/시간이다.

| 방법 | MAE (대/시간) | RMSE (대/시간) | bias | 일별 합계 MAE (대/일) |
|---|---:|---:|---:|---:|
| 모델 hgb-v1 | 47.53 | 72.95 | -25.32 | 902.1 |
| 시간대 평균 기준 | 94.78 | 138.53 | -61.79 | 2,058.6 |
| 전체 평균 기준 | 170.51 | 226.03 | -60.89 | 2,047.0 |

- 시간대 평균 기준보다 MAE가 49.9% 줄어 두 기준을 모두 통과했다(`passed: true`).
- 학습 MAE는 17.66으로 평가 MAE(47.53)보다 훨씬 낮다. 학습 기간에 맞춰진 부분이 있고, 아래의 수요 증가 추세도 원인이다.
- 허리케인 샌디로 운영이 멈춘 2012-10-29~30을 빼도 MAE는 47.42로 거의 같다. 그 이틀은 행이 12개뿐이다.

월별 MAE (대/시간)

| 월 | 실제 평균 | 모델 | 시간대 평균 기준 |
|---|---:|---:|---:|
| 2012-09 | 303.6 | 38.93 | 131.82 |
| 2012-10 | 280.8 | 50.17 | 115.75 |
| 2012-11 | 212.6 | 47.85 | 62.25 |
| 2012-12 | 166.7 | 53.04 | 70.31 |

평균 수요가 240대인 시간대에서 평균 48대 정도 틀린다. 시간대별 재배치 규모를 정하는 용도로는 단순 방법보다 오차가 절반이다. 다만 bias가 -25라 전체적으로 적게 예측한다. 2012년 수요는 계속 늘었는데, 학습 자료의 2012년은 1~8월뿐이라 가을 이후의 증가를 다 반영하지 못했다.

## 3. 정상 동작 검사

[samples/service_cases.json](../samples/service_cases.json)의 12개 사례를 Lambda 핸들러([lambda_src/lambda_function.py](../lambda_src/lambda_function.py))에 보낸다. 모델 품질과 별개로, 서비스가 정상 입력을 처리하고 잘못된 입력을 막는지 본다. 같은 사례를 클라우드 Lambda에도 보낸다(`smoke` 단계).

200 응답에서는 공통으로 다음을 확인한다.
- 예측이 0 이상의 정수다.
- 모델 버전과 sha256이 metadata.json과 같다.
- 실행 환경의 scikit-learn 버전이 학습할 때와 같다.

| 사례 | 확인 내용 | 로컬 |
|---|---|---|
| normal_one_hour | 정상 1건, 200 | 통과 (647대) |
| normal_day_24h | 하루 24건, 200, 두 번 보내 같은 응답 | 통과 |
| target_field_ignored | 정답 `cnt: 999`를 넣어도 예측이 같고 경고가 붙음 | 통과 |
| year_outside_training | 2026년, 200, "학습 기간" 경고 | 통과 |
| missing_humidity, hour_out_of_range, weather_out_of_range, temp_as_string, humidity_out_of_range | 400과 틀린 필드 이름 | 통과 |
| empty_instances, no_instances_key, too_many_instances (1,001건) | 400과 오류 코드 | 통과 |

결과는 [results/service_check/local.json](../results/service_check/local.json)이고, 12개 모두 통과했다.

예시로 2012-12-03(월) 하루 24시간을 넣었다(관측 날씨를 예보 대신 사용). 시간당 MAE는 34.75대이고, 하루 합계는 실제 6,234대, 예측 5,626대다.

테스트(`python -m pytest -q`) 59개가 모두 통과한다. 범위는 다음과 같다.
- 입력 변환과 오류 응답(시각 없는 날짜, 지나치게 큰 수, 분·초와 시간대 경고, 반올림 포함), 원자료 점검과 분할
- Lambda 핸들러의 오류 경로: 모델 경로 없음, sha256 불일치, 깨진 모델 파일, 입력 개수가 다른 모델, 예측 중 예외, 실패 뒤 복구, S3 객체 버전이 붙은 경로 해석
- 배포 전 확인: 평가 불합격, 다른 모델, 바뀐 합격 기준이나 평가 자료, 검사 뒤 바뀐 코드, 오래된 zip
- 실행 기록: 실패하거나 Ctrl+C로 멈추면 뒤 단계를 멈추고 정상 결과를 덮지 않는지, 결과 옮기기가 중간에 실패하면 되돌리는지, 계정 ID와 경로와 IAM 사용자 이름 가리기
- Lambda 응답 해석: REPORT 로그, 처리되지 않은 예외, 객체가 아닌 응답
- 모의 AWS(moto): 배포 2회, 서비스 검사, 클라우드 평가, 상태 조회, 정리. 오류 재현용 배포가 정상 배포 기록을 덮지 않는지. S3 권한 오류로 상태를 확인하지 못하면 정리를 실패로 기록하는지. 배포 전 확인에 걸리면 AWS 자원을 만들지 않는지. 프로필 없이 환경 변수 키만 있으면 AWS에 접속하지 않는지

moto 테스트에서는 배포 전 확인을 대체하고, 작은 가짜 zip을 올리고, Lambda 호출을 같은 핸들러를 로컬에서 부르는 것으로 바꿨다. moto가 Lambda 함수를 실제로 실행하지 못하기 때문이다. 실제 AWS 결과는 [cloud.md](cloud.md)에 따로 적는다.

크리스마스부터 새해 사이의 평일은 공식 공휴일이 아니어서 입력으로는 평범한 근무일이다. 그런데 출근 시간 대여가 평소(약 600대)의 1/3 정도로 줄었다. 연말 휴가철이라 출근하는 사람이 적었던 것으로 보인다. 모델은 맑은 평일 아침 8시로 보고 높게 예측했다. 11-23(추수감사절 다음 날 금요일, 실제 94대, 예측 464대)도 같은 유형이다.

학습 자료에도 같은 패턴이 있었다. 2011-12-27~30(화~금) 08시 대여는 164~217대로, 두 주 전 같은 요일(12-13~16, 400~467대)의 절반 수준이었다. 하지만 모델 입력에는 월(12월)만 있고 며칠인지, 연휴 주간인지는 없어서 12월 초와 말을 구분하지 못했다. 정보는 학습 자료에 있었지만 입력 특성으로 표현되지 않은 것이 원인이다.

개선 방향은 "연말 연휴 주간", "공휴일 다음 날" 같은 표시를 입력에 넣거나 연중 일자(day of year)를 특성으로 쓰는 것이다. 평가 자료를 보고 모델을 고치면 평가가 공정하지 않으므로 이번 버전에서는 고치지 않았다.

반대 유형도 있다. 2012-11-12(재향군인의 날 대체 공휴일)는 공식 공휴일인데도 08시 실제 대여가 540대로 평일 수준이었고, 모델은 212대로 예측했다. 공휴일 표시만으로는 실제로 쉬는 사람이 얼마나 되는지 알 수 없다.

## 5. 한계와 측정하지 못한 부분

- 날씨는 관측값이다. 실제 서비스에서는 하루 전 예보를 넣게 되므로 예보 오차만큼 정확도가 더 낮아질 것이다. 예보 자료가 없어 그 차이는 측정하지 못했다.
- 2011~2012년 워싱턴 D.C. 한 도시의 자료다. 다른 도시나 최근 연도에서는 수요 규모가 다르다. 2013년 이후 날짜는 2012년 수준으로 계산하고 경고를 붙이는데, 이 계산이 맞는지는 확인하지 못했다.
- 평가 기간이 9~12월뿐이라 봄과 여름의 성능은 이 평가로 알 수 없다.
- 풍속 0 값(2,180행)이 실제 무풍인지 결측인지 구분하지 못했다. 풍속 단위(km/h)도 가정이다.
- 기온 정규화 식이 두 가지로 적혀 있어 하나를 골랐다(근거는 [data_and_model.md](data_and_model.md)). 사용자가 넣은 °C의 해석이 그 선택에 달려 있다.
- 시스템 전체 수요만 예측한다. 재배치에 필요한 정류소별 수요는 예측하지 않는다.
- 대여가 0건인 시간은 원자료에 행이 없는 것으로 보인다. 그래서 0건에 가까운 시간대의 오차는 실제보다 작게 측정되었을 수 있다.
- 예측이 얼마나 확실한지(예측 구간)는 제공하지 않는다.
