# 결과 평가

평가 코드: [bikeml/evaluate.py](../bikeml/evaluate.py), 서비스 검사: [bikeml/servicecheck.py](../bikeml/servicecheck.py)
결과 파일: [results/evaluation/](../results/evaluation/), [results/service_check/](../results/service_check/)

## 1. 평가 자료와 판단 기준 (평가 전에 정함)

- **평가 자료**: 2012-09-01 ~ 2012-12-31의 2,888시간. 학습에 쓰지 않은 미래 기간입니다.
- **비교 대상(같은 평가 자료)**:
  - `baseline_mean`: 학습 자료 전체의 시간당 평균(179.3)을 항상 답함
  - `baseline_hour_mean`: 학습 자료에서 (시각, 근무일 여부)별 평균을 답함. 출퇴근 시간 효과를 아는 단순 방법
- **지표**: 운영 담당자는 "몇 대가 대여될지"로 계획하므로 단위가 그대로 남는 지표를 골랐습니다.
  - MAE = 평균(|예측 − 실제|), 단위 대/시간. 기본 지표
  - RMSE = √평균((예측 − 실제)²), 단위 대/시간. 큰 오차에 더 민감
  - bias = 평균(예측 − 실제). 음수면 적게 예측함
  - 일별 합계 MAE = 하루 합계를 비교한 MAE, 단위 대/일
- **합격 기준** ([config/pipeline.json](../config/pipeline.json) `evaluation.criteria`):
  1. 두 기준 방법보다 MAE가 낮을 것
  2. 시간대 평균 기준(`baseline_hour_mean`)보다 MAE를 30% 이상 줄일 것
  기준을 넘지 못하면 `evaluate` 단계가 실패로 끝나고 배포 단계로 넘어가지 않습니다.

## 2. 품질 결과

`python -m bikeml run local` 실행 결과([results/evaluation/metrics.json](../results/evaluation/metrics.json))입니다. 평가 자료의 실제 평균은 240.2 대/시간입니다.

| 방법 | MAE (대/시간) | RMSE (대/시간) | bias | 일별 합계 MAE (대/일) |
|---|---:|---:|---:|---:|
| **모델 hgb-v1** | **47.53** | **72.95** | −25.32 | **902.1** |
| 시간대 평균 기준 | 94.78 | 138.53 | −61.79 | 2,058.6 |
| 전체 평균 기준 | 170.51 | 226.03 | −60.89 | 2,047.0 |

- 시간대 평균 기준보다 MAE가 **49.9% 줄었습니다** → 기준 1, 2 모두 통과 (`passed: true`).
- 학습 MAE는 17.66으로, 평가 MAE(47.53)보다 훨씬 낮습니다. 학습 기간에 맞춰진 부분이 있고, 아래의 수요 증가 추세도 원인입니다.
- 허리케인 샌디로 운영이 멈춘 2012-10-29~30을 빼도 MAE는 47.42로 거의 같습니다. 그 이틀은 행이 12개뿐이라 전체 점수에 주는 영향이 작습니다.

월별 MAE (대/시간):

| 월 | 실제 평균 | 모델 | 시간대 평균 기준 |
|---|---:|---:|---:|
| 2012-09 | 303.6 | 38.93 | 131.82 |
| 2012-10 | 280.8 | 50.17 | 115.75 |
| 2012-11 | 212.6 | 47.85 | 62.25 |
| 2012-12 | 166.7 | 53.04 | 70.31 |

**결과의 의미**: 평균 수요가 240대인 시간대에서 평균 ±48대 정도 틀립니다. 시간대별 재배치 규모를 정하는 용도로는 단순 방법보다 두 배 정확합니다. 다만 bias가 −25로, 전체적으로 적게 예측합니다. 2012년 수요가 계속 늘었는데, 학습 자료의 2012년은 1~8월뿐이라 가을 이후의 증가를 다 반영하지 못했습니다.

## 3. 정상 동작 검사

[samples/service_cases.json](../samples/service_cases.json)의 13개 사례를 서비스 핸들러([lambda_src/lambda_function.py](../lambda_src/lambda_function.py))에 보냅니다. 모델 품질과 별개로 **서비스가 정상 입력을 처리하고 잘못된 입력을 막는지** 봅니다. 같은 사례를 클라우드 Lambda에도 보냅니다(`smoke` 단계).

| 사례 | 확인 내용 | 로컬 |
|---|---|---|
| normal_one_hour | 정상 1건 → 200, 0 이상 정수, 모델 버전·sha256 일치 | 통과 (647대) |
| normal_day_24h | 하루 24건 → 200, 24건, 두 번 보내 같은 응답 | 통과 |
| http_body_string | `{"body": "..."}` 형태 → 첫 사례와 같은 예측 | 통과 |
| target_field_ignored | 정답 `cnt: 999`를 넣어도 예측이 같고, 경고가 붙음 | 통과 |
| year_outside_training | 2026년 → 200, "학습 기간" 경고 | 통과 |
| missing_humidity, hour_out_of_range, weather_out_of_range, temp_as_string, humidity_out_of_range | 400 + 틀린 필드 이름 | 통과 |
| empty_instances, no_instances_key, too_many_instances(1,001건) | 400 + 오류 코드 | 통과 |

결과: [results/service_check/local.json](../results/service_check/local.json) — **13/13 통과**.
단위 테스트(`python -m pytest -q`) 23개는 입력 변환, 오류 응답, 원자료 점검, 분할을 검사하며 모두 통과합니다.

예시로 2012-12-03(월) 하루 24시간을 넣은 결과입니다(관측 날씨를 예보로 사용). 시간당 MAE는 34.75대이고, 하루 합계는 실제 6,234대, 예측 5,626대입니다.

## 4. 잘못된 결과 한 건 분석: 2012-12-27(목) 08시

| | 값 |
|---|---|
| 입력 | 평일, holiday=false, 날씨 1(맑음), 4.2°C |
| 실제 | **208대** |
| 모델 예측 | **707.5대** (오차 +499.5, 평가 기간 최대) |
| 시간대 평균 기준 | 445.2대 |

같은 시각(08시)의 앞뒤 7일 ([results/evaluation/worst_case_context.csv](../results/evaluation/worst_case_context.csv)):

| 날짜 | 요일 | 공휴일 | 실제 | 예측 |
|---|---|---|---:|---:|
| 12-20 | 목 | | 599 | 573 |
| 12-21 | 금 | | 472 | 432 |
| 12-24 | 월 | | 66 | 495 |
| 12-25 | 화 | ✔ | 11 | 87 |
| 12-26 | 수 | | 31 | 294 |
| **12-27** | **목** | | **208** | **708** |
| 12-28 | 금 | | 239 | 510 |

**원인**: 크리스마스부터 새해 사이의 평일은 공식 공휴일(holiday)이 아니어서 입력상 평범한 근무일입니다. 하지만 휴가를 낸 사람이 많아 출근 시간 대여가 평소(약 600대)의 1/3 정도로 줄었습니다. 모델은 "맑은 평일 아침 8시"로 보고 높게 예측했습니다. 11-23(추수감사절 다음 날 금요일, 실제 94대, 예측 464대)도 같은 유형입니다.

학습 자료에도 같은 패턴이 있었습니다. 2011-12-27~30 08시 대여는 164~217대로, 두 주 전(400~467대)의 절반이었습니다. 하지만 모델에는 "월(12월)"만 있고 "며칠인지"나 "연휴 주간인지"가 없어서, 12월 초와 말을 구분하지 못했습니다. 정보가 학습 자료에는 있었지만 **입력 특성으로 표현되지 않은 것**이 원인입니다.

**개선 방향(다음 버전 후보)**: "연말 연휴 주간", "공휴일 다음 날" 같은 표시를 입력에 추가하거나, 연중 일자(day of year)를 특성으로 넣는 방법이 있습니다. 이번 버전에서는 평가 자료를 본 뒤 모델을 고치면 평가가 공정하지 않게 되므로 고치지 않았습니다.

반대 유형도 있습니다. 2012-11-12(재향군인의 날)는 공식 공휴일이지만 민간 회사는 대부분 출근해서 08시 실제 540대, 예측 212대였습니다. 공휴일 표시 하나만으로는 "실제로 쉬는 사람이 얼마나 많은지"를 알 수 없습니다.

## 5. 한계와 측정하지 못한 부분

- **날씨는 관측값입니다.** 실제 서비스에서는 하루 전 예보를 넣게 되며, 예보 오차만큼 정확도가 더 낮아질 것입니다. 예보 자료가 없어 그 차이는 측정하지 못했습니다.
- **2011~2012년 워싱턴 D.C. 한 도시의 자료**입니다. 다른 도시나 최근 연도에 쓰면 수요 규모가 다릅니다. 2013년 이후 날짜는 2012년 수준으로 계산하며(경고 표시), 이 계산이 맞는지는 확인하지 못했습니다.
- 평가 기간은 9~12월(가을·겨울)뿐이라 봄·여름 성능은 이 평가로 알 수 없습니다.
- 풍속 0 값(2,180행)이 실제 무풍인지 결측인지 구분하지 못했습니다. 풍속 단위(km/h)도 가정입니다.
- 기온 정규화 식이 두 가지로 적혀 있어 하나를 골랐습니다(근거는 [data_and_model.md](data_and_model.md)). 사용자가 넣은 °C 값의 해석이 그 선택에 달려 있습니다.
- 시스템 전체 수요만 예측합니다. 재배치에 필요한 정류소별 수요는 예측하지 않습니다.
- 대여가 0건인 시간은 원자료에 행이 없는 것으로 보여, 0건에 가까운 시간대의 오차는 실제보다 작게 측정되었을 수 있습니다.
- 예측 구간(얼마나 확실한지)은 제공하지 않습니다.
